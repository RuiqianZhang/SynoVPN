# SA6400 / DSM 7.4.1-90080 Update 1 构建目标

目标来自用户提供的 DSM 版本。NAS 上已完成构建与容器内的真实引擎检查，尚未安装到 DSM 或验证客户端隧道。Synology 官方 CPU 表将 SA6400 列为 x86_64 / Epyc7002，套件 INFO 因此使用 `arch="epyc7002"`，程序编译为 Linux amd64。

参考：[Synology CPU / 套件架构表](https://kb.synology.com/de-de/DSM/tutorial/What_kind_of_CPU_does_my_NAS_have)。

## 完整构建

在已有 Go 1.26+、Python 3 和 Docker BuildKit 的构建主机中运行：

```sh
python3 tools/build.py --target sa6400 --build-runtime --smoke
```

预期产物：`dist/SynoVPN-0.2.0-sa6400-epyc7002.spk` 及 SHA-256 校验文件。

没有 charon、架构不符或引擎检查未通过时不生成目标 SPK。目标记录随包保存为 `build-target.json`，不会把构建通过标记成已通过 DSM 实机验收。

## 使用 NAS 的 Container Manager 构建

专用构建资料包内含 `docker-compose.yml`、`source/` 和新建的 `dist/` 输出目录。项目放在健康存储空间中的独立目录。

构建采用官方 Go/Alpine 基础映像，在映像内安装编译工具、运行单元测试并编译静态 strongSwan。Go 依赖随 vendor 提供。自检容器运行时禁用网络、不发布端口、不挂载 Docker socket；该项目的 `dist/` 目录为唯一可写的宿主机挂载，`source/tools/` 仅只读挂载，以便复用编译好的引擎更新打包与检查脚本。只在自己的网络命名空间中授予 NET_ADMIN/NET_RAW/NET_BIND_SERVICE；DAC_OVERRIDE 用于写入新建输出目录。不挂载其他 NAS 数据，不使用 privileged 或 host 网络。运行容器绑定 CPU 0、1，内存限制为 2 GB；该 NAS 内核不支持 NanoCPUs 和 PIDs 限额，128 进程设置被 Docker 忽略。

已生成文件：`/volume3/docker/synovpn-sa6400-build/dist/SynoVPN-0.2.0-sa6400-epyc7002.spk`（约 24.3 MB）和同名 `.spk.sha256` 文件。自动下载被浏览器取消，需从 File Station 下载后独立核对归档及校验值。更新构建镜像时应使用新标签，并核对磁盘中的 `docker-compose.yml` 与实际容器映像；仅重启旧容器不会应用源码改动。

自检通过后，容器才会生成完整 SPK，然后退出。构建不安装 VPN 套件、不启用宿主机转发、不修改 NAS 防火墙；安装需要拿到 SPK 后另行执行。

## 构建与设备验收分开

通过构建仅证明二进制、VICI 配置和证书流程能在 Linux 容器中运行。DSM 安装后的套件账号、CGI 身份、权限、转发和真实客户端连接仍需在 SA6400 上逐项验证。
